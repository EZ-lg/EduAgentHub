## 一、P4 已完成内容

### 1.1 后端

- **`backend/services/conversation_service.py`（新建，核心）** — AI 对话式采集业务逻辑
  - `start_conversation(db, subject_id)`：幂等开始/恢复会话
    - 该学科存在 `in_progress` 会话 → 直接复用（页面刷新不重复建会话）
    - 无则新建会话；**已配置 LLM 且会话为空 → 自动生成第一条 AI 问题**（F4.1）
    - 首问失败/未配置 → 留空会话返回，前端可重试或引导去设置页
    - 返回 `{conversation, configured, subject_name, student_name}`
  - `handle_message(db, subject_id, conversation_id, message_text)`：
    - 追加用户消息 → 一次 LLM 调用（conversation.txt）输出 JSON `{"reply","enough"}` → 追加 AI 回复
    - `enough=true` 仅是 **should_end 信号**（AI 收尾语已作为 reply），**不改 status**，用户可补充或手动结束
    - 返回 `{conversation_id, reply, should_end, summary:null, messages, status}`
  - `end_conversation(db, subject_id, conversation_id)`：
    - conversation_end.txt 生成学情总结 → 追加为最后一条 AI 消息（前缀「【学情总结】\n」）→ status 置 `completed`
    - 幂等：已 completed 时返回最后一条 AI 消息内容
    - 返回 `{conversation_id, summary, report_id:null, messages, status}`
  - 内部工具：`_extract_json`（剥```围栏 + 取首个{} + json.loads）、`_parse_reply`（解析失败→整段当 reply + enough=False）、`_call_llm`（未配置抛503/失败抛502，由 handle_message 兜底成友好气泡）、`_display_history`（ai/user → assistant/user）、`_subjects_info`（该生其他活跃学科，防 AI 跨学科乱问）
  - 异常路径：message 里 LLM 异常 → 追加「抱歉，AI 服务暂时不可用…」气泡，不崩会话；未配置 → 追加「请先在系统设置配置 LLM」提示
- **`backend/routers/conversations.py`（重写）** — 4 个接口全部接 service
  - `_resolve_conversation_id`：body 缺省时兜底为该学科最新 in_progress 会话（兼容需求文档 §6.2 请求体只带 message 的写法）
  - `GET /conversations` 改用 `conversation_to_dict`（messages 返回**解析后的数组**，不是 JSON 字符串）
- **Prompt 模板完善**（Jinja2 StrictUndefined，变量必须全传）：
  - `conversation.txt`：变量 `student_name, subject_name, history, subjects_info`。学情访谈助手；一次一问；信息足够→收尾语+`enough=true`；**强制输出 JSON `{"reply","enough"}`**
  - `conversation_end.txt`：变量 `student_name, subject_name, history`。生成结构化学情总结（150-250字，未采集标注）

## 二、关键架构决策

| 决策 | 说明 |
|------|------|
| start 幂等 | in_progress 会话复用；completed 后 start 新建会话（F4.8 重新建档） |
| 一次调用生成回复+结束判断 | conversation.txt 输出 `{"reply","enough"}`，省一半成本；JSON 解析失败整段当 reply |
| **should_end 不等于结束** | AI 说收尾语时 only `should_end=true` + 不改 status，用户可补充/手动结束；总结统一在 end 生成（满足 F4.4/F4.5/F4.6） |
| 消息数组返回 | 后端返回 `messages`（解析数组）+ `status`，前端权威重渲染，杜绝本地追加与后端漂移 |
| P4 不建报告 | end 返回 `report_id:null`，草稿 Report 与完整报告留 P5 |
| 对话不查知识库 | RAG ❌（仅 P5 报告 / P8 问答用） |
| 角色存储 | messages_json 用 `ai`/`user`（与需求文档一致），转 LLM 时映射 assistant/user |

## 五、注意事项（给下一个 AI）

1. **LLM 调用入口**：`ai_manager.get_llm()`，`is_configured('llm')` 检查；未配置时对话端返回友好提示，引导去设置页
2. **messages_json 角色约定**：存 `ai`/`user`；转 LLM 用 `_display_history` 映射 `assistant`/`user`。P5 起读历史总结时沿用
3. **版本号纪律（改前端必做！）**：改任何前端文件后递增 `index.html` 里 `APP_VERSION` + 所有 `?v=` 引用（当前 8）
4. **对话页刷新陷阱**：`window.currentPageRefresh` 在 completed 状态 no-op，否则切回标签页会自动新建会话冲掉总结；in_progress 时重调 start（幂等）
5. **should_end 语义**：AI 说「信息差不多了」后用户仍可补充；补充后 AI 会重新判断（可能继续追问或再次收尾）
6. **测试方法**：可用 `custom_openai` provider + 本地 mock OpenAI 兼容服务（POST `/chat/completions`）做全流程验证；或配真实 key
7. **运行前激活 venv**：`source venv/Scripts/activate`，`python main.py`（8888 端口，自动开浏览器）
8. **git**：P4 等用户验收后再 commit + push；tag 打 `P4-完成`
9. **数据库当前为干净状态**：0 学生 / 0 学科 / 0 会话 / llm_config 空（用户需自行配置 LLM 后体验对话）
